# IO

A system does IO by putting ops on its own submission queue and taking
results from its own completion queue. It never makes a syscall. What
executes the ops is chosen per target:
- io_uring in flight;
- a readiness emulation on Unix development hosts;
- simulated peripherals, which are themselves systems.

A system cannot tell which it has.

A target creates **resources** by name: a serial port, a file, a directory,
a socket, a simulated serial line, or another target's endpoint. A system holds a
**capability** to each resource it was granted, and it has no other way to
do IO.

```
cycle N:    systems ──SQ rings──▶ io_submit ─┬─▶ Reactor ─▶ Os (io_uring or Poll)
                                             └─▶ device-end rings ─▶ model systems
                                  io_complete ◀── Reactor, model replies
cycle N+1:  systems ◀──CQ rings── io_complete
```

An op submitted in cycle N completes in cycle N+1 or later, never during
the call that submitted it.

## A system

```rust
struct GpsState {
    rx: Slot<Read>,
    tx: Slot<Write>,
    configured: bool,
    nmea: Nmea,
}

impl GpsState {
    fn new(io: &IoInit) -> Self {
        Self {
            rx: Slot::Idle(io.alloc(256)),
            tx: Slot::Idle(io.alloc_from(PMTK_RATE_10HZ)),
            configured: false,
            nmea: Nmea::default(),
        }
    }
}

/// Sets the receiver to 10 Hz, then publishes each fix it reports.
#[system]
fn gps(#[state] s: &mut GpsState, uart: &Cap<Uart>, fix: &mut Output<Gps>, log: &mut Log) {
    match s.tx.poll() {
        Some(Ok(_)) => s.configured = true,
        Some(Err(e)) => log.fault("gps_config", e),
        None => {}
    }
    match s.rx.poll() {
        Some(Ok(_)) => s.nmea.push(s.rx.bytes()),
        Some(Err(e)) => log.fault("gps_read", e),
        None => {}
    }
    while let Some(f) = s.nmea.next() {
        let _ = fix.write(&Gps::from(f));
    }
    if !s.configured && let Some(cmd) = s.tx.take_idle() {
        s.tx = Slot::Busy(uart.write(cmd));
    }
    if let Some(buf) = s.rx.take_idle() {
        s.rx = Slot::Busy(uart.read(buf));
    }
}

table.register("gps", gps(), GpsState::new)?;
```

Each cycle, the system takes what completed, acts on it, and submits what
comes next. A failed config write is retried next cycle, because the
command's buffer comes back unchanged.

A sequence awaits the same calls. A `Pending` resolves to the result and the
buffer, `let (res, buf) = uart.read(buf).await;`, and `Slot::poll` unpacks
the same pair.

### Handles

- **`Cap<K>`.** A `Cap<K>` parameter is the capability a system was granted.
  It derefs to `Handle<K>`.
- **Methods by interface.** A handle's methods depend on its interface `K`:

  | Interface | Methods |
  |---|---|
  | `Uart` | `read`, `write`, `configure`, `flush` |
  | `Can`, `Udp`, `Stream` | `recv`, `send` |
  | `File` | `read`, `write` (at an offset), `fsync` |
  | `GpioLine` | `get`, `set` |
  | `Dir` | `open` |
  | `Listen` | `accept` |
  | `Dial` | `connect` |
  | any | `close` |

- **Derived handles.** `open`, `accept`, and `connect` complete with a new
  handle derived from the one they were called on: a `File` or a
  `Stream`.
  - A system never names an address. `connect` dials whatever its `Dial`
    resource resolves to.
  - Paths are relative to a `Dir` the system holds.
- **Index and generation.** A handle is an index into its system's handle
  table plus a generation. A closed handle is stale, and every later op on
  it fails with `Stale`.
- **Its own queue.** A handle submits only to its own system's queue.

### Pending ops

- **Each method returns a `Pending<O>`.** In a sequence, `Pending` is a
  future that `SequenceStep` polls once per cycle.
- **Submitting never fails at once.** If the SQ ring is full, the `Io`
  completes the op itself, with `QueueFull`, on the next poll. A stale handle
  or a refused op completes with an error next cycle. A system has one error
  path.
- **`MAX_OPS` bounds a system's ops in flight.** It is the constant 16,
  the `Record::DEPTH` of `Sqe` and `Cqe`. It sets the depth of the system's
  SQ and CQ ports, and sizes the reactor's tables.
- **Dropping a `Pending` does not cancel the op.** Its result is discarded
  when it lands. `cancel()` cancels it.

### Buffers

- **Allocated in the constructor.** A constructor may take `&IoInit`,
  alongside its params: `Fn(&IoInit) -> S`, `Fn(P, &IoInit) -> S`, or
  `Fn(P, &IoInit) -> Result<S, ParamError>`.
  - `io.alloc(len)` allocates a buffer. `io.alloc_from(bytes)` allocates one
    already filled. Neither fails at the call. When the table cannot give
    the memory, the make fails afterward with `ParamError::IoMemory`.
  - Build binds a system's ports before it runs the constructor, so
    `IoInit` reaches the system's queue.
  - `IoInit` exists only while the system is made, so a system cannot
    allocate IO memory in steady state.
- **The buffer table.** Buffers live in the system's buffer table: one
  arena of bytes with a directory of entries `(offset, cap, len)` at its
  start. A `Buf` is a slot index into it, never a pointer, that derefs to
  its filled bytes.
  - While the system is made, `alloc` appends to the arena, which may grow
    and move.
  - The arena freezes when the io steps are built. Only then are pointers
    handed to the kernel, and its address never changes again. io_uring
    registers each system's arena as one fixed buffer.
  - A dropped `Buf` frees its entry. Its bytes are reused only after a
    remake.
  - **A `Reset` or `Load` quiesces.** It cancels the system's ops in
    flight. The system is remade, or the new candidate loaded, on the
    first cycle with none left in flight, at least a cycle later. The new
    ctor allocates into the same arena from its start, within its
    capacity. Asking for more fails the make with `IoMemory`, naming the
    bytes needed and available. So the first make sizes the arena for
    every later one.
- **Ops take buffers by value.** The completion hands the buffer back with
  the result.
- **`Slot<O>`** keeps a buffer at home in state. It is either `Idle(Buf)` or
  `Busy(Pending<O>)`.
  - `take_idle()` takes the buffer to start an op.
  - `poll()` returns the op's result once it lands, and puts the buffer back
    in `Idle`.
  - `bytes()` reads the idle buffer.

Handles, pending ops, and buffers each hold an `Rc` to their system's queue
or buffer table, which is how their methods work. Underneath, each is an
index. The `Rc`s are dropped with the system's state, which closes its
derived handles.

### `Io`

`io: &Io` is the base API under the handle methods: submission by raw
handle and token. A system rarely takes it.

A system gets a queue pair when its signature names a `Cap<K>`. A
`DeviceSide<K>` brings its own request and reply rings instead. A system
with no `Cap<K>` has no buffer table, so a
constructor that allocates on it fails its make, at build.

## Resources and capabilities

There are two layers:
- **A resource** is the thing itself: an opened tty, a socket, a
  directory, a simulated serial pair. A target creates each one once, by name.
- **A capability** is one system's authority over a resource. It is an
  entry in that system's handle table.

Passing a resource to a system is a **grant**. Each grant mints a new
capability.

```python
gps1 = fsw.resource("gps1", Tty("/dev/ttyTHS0", baud=9600))
# or, for a sim:
gps1 = fsw.resource("gps1", SimUart())
fsw.sim("gps_dev", GpsReceiver(dev=gps1, truth=plant.body))

gps = fsw.add("gps", GpsDriver(uart=gps1))         # a grant: gps gets a Cap<Uart>
cold = fsw.add("cold_start", ColdStart(uart=gps1)) # another grant, to the same resource
```

- **Backing.** Each resource is backed one of three ways:
  - **Real:** one of a closed set of kinds: `Tty`, `Can`, `GpioLine`,
    `Udp`, `File`, `Dir`, `TcpListen`, and `TcpConnect`. Build opens it,
    with its setup: termios, CAN filters, a GPIO line request, a bind, and
    hands the descriptor to the `Os` with `register`. A failure fails the
    build. A `TcpConnect` is not opened. It is data, its address, which
    build hands to the `Os`'s constructor. Each `connect` on it makes a
    new socket.
  - **Sim:** a two-ended simulated resource, such as `SimUart`, whose device
    end a model system serves (see "Simulation").
  - **Peer:** another target's resource, resolved when it connects.
- **Interfaces.** Each real or sim kind provides one interface. Build checks that a
  `Cap<Uart>` parameter is granted a resource that provides `Uart`, the same
  way it checks a port's record type.
- **One name everywhere.** Config, `io_status`, and the panel
  all use the resource's name. Across targets it is
  `{namespace}.{resource}`.
- **Sharing.** Several systems may hold capabilities to one resource.
  Sharing has the OS's semantics: two readers of a stream split its
  bytes, and two writers may interleave.
- **Lifetimes.** The target owns each resource for its whole life.
  - `close()` ends only the capability it was called on.
  - Derived handles close when their system is reset, dropped, or faulted.
- **Config.** All additions are fields with defaults:
  - `CoordinatorConfig` gains `resources: Vec<ResourceConfig { id,
    backing }>`, where `backing` is `Real(RealKind)`, `Sim(SimKind)`, or
    `Peer(name)`, and `seed: u64`, the target seed.
  - `SystemConfig` gains `grants: Vec<Grant { param, resource }>`. A grant
    maps a `Cap<K>` parameter to a resource id, the way an input maps to a
    producer. It never appears in the system's params.
  - `SystemDef` lists each `Cap<K>` and `DeviceSide<K>` parameter as a
    `GrantDef { param, interface, end }`. Build checks the config's grants
    against these and the resources.

What makes this a capability system:
- A system acts only through capabilities it holds.
- Every capability comes from a grant in the target file, or is derived
  from one it already holds.
- A closed capability is stale.

A wasm guest has no other way to do IO, so there this is enforced. Host and
dylib systems follow the same rule by convention.

## The `io` system

`io` is two ordinary systems, `io_submit` and `io_complete`. The Python
builder's `to_config` appends them after the systems added with
`fsw.add`, with the systems added through `fsw.sim` between them. Sim
systems get handles like any other, so edges and channels name them. The
coordinator does not change.

- **Every system's `Io` is a pair of ports.**
  - `io_sq` is an output carrying `Sqe` records.
  - `io_cq` is an input carrying `Cqe` records.

  A system with several `Cap<K>` parameters still has one pair.
- **`io_submit` and `io_complete` cover every system.**
  - `io_submit` reads every `io_sq` through `DynInputs`, in step order.
  - `io_complete` writes one CQ per system through `DynOutputs`.
  - A system reads its `io_cq` through a loop edge, so it sees the
    completions `io_complete` posted at the end of the previous cycle.
- **Ops reach the OS the cycle they are submitted.** The kernel works on
  them before the next cycle starts.
- **One shared reactor.** `io_submit`'s make opens the real resources,
  builds the coordinator thread's `Reactor`, and stores it in `MakeCx.io`
  with the members, the target's `Tables`, and the counters.
  `io_complete`'s make takes it from there. Both steps refuse `thread=` and
  `channel=`.
- **Routing by backing.** `io_submit` sends each op by its resource's
  backing. A real op goes to the reactor. A sim op is written to the
  resource's device-end request ring. `io_complete` reaps the reactor and
  drains the model replies the same way. Both map tokens through one
  table.
- **One backing kind per target, for now.** Build refuses a target whose io
  systems serve both a real and a sim resource.
- **`io_status`.** `io_complete` has an `io_status` output of one
  `ResourceStatus` per resource. `io_submit` counts ops submitted and bytes
  out, and `io_complete` counts ops completed and failed and bytes in.
  Like `LinkStatus`, a resource's status is written when it changes.

### Ops

`Sqe` and `Cqe` are `#[repr(C)]` values with a hand-written `Record` impl.
`encode` returns the value's own bytes, and `decode` checks them with
zerocopy's `TryFromBytes`. They are neither `Frame`s nor serde messages.

```rust
#[repr(C)]
pub struct Sqe { pub token: Token, pub handle: RawHandle, pub op: Op } // 48 bytes

#[repr(C)]
pub struct Cqe { pub token: Token, pub status: IoStatus, pub out: Out } // 40 bytes

#[repr(C, u8)]
pub enum Op {
    Read { buf: BufRef, offset: u64 }, // u64::MAX: the current position
    Write { buf: BufRef, offset: u64 },
    Recv { buf: BufRef },
    Send { buf: BufRef },
    SendTo { buf: BufRef, addr: RawAddr },
    Open { path: BufRef, flags: OpenFlags },
    Accept,
    Resolve,
    Connect { addr: RawAddr }, // from the `Resolve` before it
    Close,
    Fsync,
    Tty(TtyOp),
    Gpio(GpioOp),
    Cancel { target: Token },
}

#[repr(C, u8)]
pub enum Out { Unit, Len(u32), Handle(RawHandle), Addr(RawAddr) }
```

- **Byte order.** The sketch shows plain types. Every field is a zerocopy
  little-endian type of alignment one (`U32<LE>`, `U64<LE>`), and each
  enum's variants are padded by hand to one size, so the layout has no
  padding. Constructors and getters hide this.
- **`IoStatus`** is zero on success, or an error code.
- **`RawAddr`** is a fixed-size socket address.
- **No pointers.** Ops are plain bytes, so they can be logged, compared in
  tests, and copied across the guest ABI.

## The reactor

A `Reactor` takes ops to an `Os`, and brings the completions back. The
coordinator thread has one.

```rust
pub trait Os {
    /// Queues an op. Never fails: a full queue comes back from `reap` as `QueueFull`.
    fn push(&mut self, sqe: Sqe);
    /// Hands queued ops to the kernel. Never blocks.
    fn submit(&mut self);
    /// Takes every completion that has landed.
    fn reap(&mut self, done: &mut Vec<Cqe>);
    /// Takes ownership of an opened resource; ops name the handle it returns.
    fn register(&mut self, fd: OwnedFd, class: FdClass) -> RawHandle;
}

impl Reactor {
    pub fn new(os: Box<dyn Os>, limits: Limits) -> Self;
    pub fn source(&mut self, table: Rc<BufTable>) -> SourceId; // build time
    pub fn push(&mut self, src: SourceId, sqe: Sqe);
    pub fn submit(&mut self);
    pub fn reap(&mut self, done: &mut Vec<(SourceId, Cqe)>);
    pub fn cancel_all(&mut self, src: SourceId);
    pub fn in_flight(&self, src: SourceId) -> usize;
}
```

- **Sources.** Each submitter is a source, registered at build with its
  buffer table. The reactor maps each source's tokens to its own, and
  stamps the source's table into every `BufRef`, so a system names only
  its own buffers.
- **`push`** queues an op. **`submit`** hands the queued ops to the `Os`.
  **`reap`** takes what has landed and returns it with its source.
- **The cycle.** `io_submit` pushes every system's real ops and calls
  `submit`, so the kernel has them this cycle. `io_complete` calls `reap`.
  What has landed by then reaches its system in N+1, and the rest on a
  later cycle.
- **The `Os`.** Two backends live in fsw-3: `UringOs`, over its own
  io_uring instance, and `PollOs`, over `polling` with nonblocking
  syscalls, for Unix development hosts. Each issues its own handles. Build
  hands it each opened resource with `register` and an `FdClass` (stream,
  datagram, listener, file, directory, tty, CAN, GPIO), which picks the
  path its ops take. A dial target is not a descriptor. Its address goes
  to the constructor, and dial target `i` gets the handle
  `RawHandle::new(i, 0)`: the first handles, before any `register`. On
  that handle, `Resolve` answers the address and `Connect` makes a new
  stream. The constructor also takes the frozen buffer tables. io_uring
  registers each table's arena once, as one fixed buffer.
- **Quiescing.** `cancel_all` cancels a source's ops in flight, and
  `in_flight` says when none are left. `Reset` and `Load` use the pair.
  The reactor's own cancels and closes take tokens from a range of their
  own, so they never fail with `QueueFull`.
- **Teardown.** Dropping the reactor cancels every op, reaps for a bounded
  number of rounds, and leaks the buffers of ops still in flight.

Every table is sized at build from the number of members times `MAX_OPS`.

Layers between the reactor and the `Os`, for faults and tracing, come
later.

## Simulation

A simulated resource has two ends, like a pty or a socketpair.
- **The host end.** Systems are granted it as an ordinary `Cap<K>`.
- **The device end.** One **model system** is granted it as a
  `DeviceSide<K>`.

A model system is an ordinary `#[system]` that serves the device end. It has
state, ports, `status`, and `log` like any other system. If it panics, it
ends alone.

```rust
/// A GPS receiver: NMEA on a UART and a pulse per second on a GPIO line.
#[system]
fn gps_receiver(
    #[state] m: &mut GpsReceiver,
    now: Timestamp,
    dev: &mut DeviceSide<Uart>,
    pps: &mut DeviceSide<GpioLine>,
    truth: &mut Input<GpsTruth>,
    faults: &mut Input<GpsFault>,
    stats: &mut Output<FifoStats>,
) {
    if let Ok(Some(t)) = truth.latest() {
        m.truth = *t;
    }
    for f in faults.drain() {
        m.apply(f);
    }
    dev.serve(now, m);
    pps.serve(now, &mut m.pps);
    let _ = stats.write(&m.stats(now));
}

table.register("gps_receiver", gps_receiver(), GpsReceiver::new)?;
```

```python
gps1 = fsw.resource("gps1", SimUart())
pps1 = fsw.resource("pps1", SimGpioLine())
fsw.sim("gps_dev", GpsReceiver(dev=gps1, pps=pps1, truth=plant.body))

gps = fsw.add("gps", GpsDriver(uart=gps1, pps=pps1))
```

- **Sim kinds.** Each sim kind provides one interface on both ends:
  `SimUart` and `SimGpioLine`. Other kinds come with their drivers.
- **Models are systems.** A model is not registered as anything else. It is
  a pack system that takes one or more `DeviceSide<K>`. One model can serve
  several resources, such as a GPS's UART and its PPS line, or every node on
  a simulated CAN bus.
- **One device end per resource.** Build checks that each sim resource is
  granted to exactly one `DeviceSide`.
- **`DeviceSide<K>`** is a request ring in and a reply ring out. Its `serve`
  advances a model to `now` and calls the interface trait for each queued
  op. It holds an op that is not ready yet, or that has latency, until a
  later serve. Latency counts serves, one per cycle. A cancel is answered
  when it arrives and is never held. The held queue is sized at build to
  `MAX_OPS` times the host grants on the resource.
- **The driver's bytes.** A request carries a `BufRef` into the driver's
  buffer table. `DeviceSide` holds an `Rc` to the target's `Tables`, shared
  through `MakeCx.io`, and reads and fills the driver's buffer
  through it. A `BufRef` that does not resolve completes `BadBuf`. Models
  run on the coordinator thread, so this is safe. Model systems in wasm
  or dylib guests are out of scope for v1.

  ```rust
  pub trait UartModel {
      /// `None` when the FIFO is empty; the read waits for a later tick.
      fn rx(&mut self, now: Timestamp, buf: &mut [u8]) -> Option<usize>;
      fn tx(&mut self, now: Timestamp, bytes: &[u8]) -> Result<usize, IoError>;
      fn configure(&mut self, now: Timestamp, cfg: &TtyConfig) -> Result<(), IoError>;
      fn tick(&mut self, now: Timestamp);
  }
  // also GpioModel
  ```

- **Realistic behavior.** A `GpsReceiver`'s `tick` encodes the true position
  as NMEA at the configured rate. A driver that stops reading overflows its
  FIFO, and a wrong baud rate gives garbage.
- **Peripheral faults.** An outage, a cold start, or a stuck register is an
  ordinary input of the model system, so a scenario or the panel can command
  it.
- **Swapping in one call.** A model's Python module may offer sugar that
  creates its sim resources, adds the model with `fsw.sim`, and returns the
  resources to grant. For example,
  `uart, pps = GpsReceiver.attach(fsw, "gps", truth=plant.body)`.

### Where model systems run

`fsw.sim` is `fsw.add` with a different position. The builder emits systems
added with `fsw.sim` between `io_submit` and `io_complete`, in the order they
were added:

```
flight systems   submit ops to their SQ rings
io_submit        drain the SQs; real ops go to the reactor, and sim ops go to
                 their device end's request ring
fsw.sim systems  read truth, serve requests, and write replies
io_complete      reap the reactor and model replies, and post each system's CQ
```

- **No extra latency.** An op submitted in cycle N reaches its model in
  cycle N, and the system sees the result in cycle N+1.
- **Same-cycle inputs.** These models run after every flight system, so they
  read this cycle's plant truth. Their outputs reach flight systems on the
  next cycle, through loop edges.
- **A model added with `fsw.add` still works.** It runs in add order and
  reads its requests through a loop edge, so a driver sees results in cycle
  N+2, deterministically. Placement is a choice, and build does not check it.
- **A model that stops leaves its ops hanging,** like an unpowered device.
  The driver's own timeout handles it.

There is no sim `Os`. `io_submit` writes a sim op to its resource's
request ring, and `io_complete` drains the reply rings. A target that mixes
real and sim resources comes later.

### Tests

A unit test calls the system fn directly. `test::cap` gives a `Cap<K>` over
in-memory rings, wired to a model the test steps by hand. A model system is
tested the same way, through `test::device::<K>()`.

```rust
let (uart, mut io) = test::cap::<Uart>(ScriptedUart::silent().fail_write(Errno::EIO));
let mut s = GpsState::new(&io.init());
for _ in 0..3 {
    gps(&mut s, &uart, &mut fix, &mut log);
    io.turn();
}
assert_eq!(io.model::<ScriptedUart>().written(), [PMTK_RATE_10HZ]);
```

Faults are injected through models: a `ScriptedUart` that fails a write,
returns a short read, or never answers.

### Threads

- **The coordinator thread's reactor** is shared by `io_submit` and
  `io_complete`.
- **Async systems keep stellarator's own IO.** They do not take `Cap<K>`
  yet. Their ops never pass through `io_submit`, and `io_status` does not
  count them.
- **Deterministic runs.** The `Thread` adapter has a deterministic mode, set
  per run.
  - The step owns the group's `Executor`, and calls `Executor::turn` once
    per cycle on the coordinator thread. No OS thread is spawned.
  - The group's clock is the cycle's time, set by the step, with a 1 µs
    tick to match `Timestamp`. `turn` never moves a clock it does not own.
  - Every task and `JoinHandle` on the group drops before its executor,
    since a `Sleep` borrows the executor's timer.
  - Mirrors copy as they do today.
  - This makes an async system's scheduling and timing deterministic. Its
    IO through stellarator is not.
- **A fixed epoch.** `Clock::Simulated { dt, epoch }` starts simulated time
  at `epoch` when it is set. Python takes `Target(.., epoch=..)`, and
  `metor run --epoch` overrides it.
- **What determinism covers.** A run is reproducible from the target seed,
  `CoordinatorConfig.seed`, and the epoch, when every resource is
  simulated, every thread group is deterministic, and no async system does
  IO. Each model has its own RNG, seeded from the target seed and its name.
  Real backends are not deterministic.

## Links and names

Links take a resource through `via=`:

```python
down = plant.resource("down", TcpListen("0.0.0.0:2240"))
plant.add("pub", Publish([sim], via=down))
fsw.add("plant", Subscribe([sim], via=down))   # a peer of plant's `down`
```

- **`via` names a resource.** Links are async systems, so they hold no
  capability. Their params carry the resource's name.
  - A `TcpListen`: build binds it, or takes the descriptor the harness
    passed down, and hands the socket to the link. The link adopts it with
    `stellarator::TcpListener::adopt`.
  - A `TcpConnect`: the link dials its address with stellarator's
    `TcpStream::connect`, with backoff.
- **The shorthands stay.** `listen=`, `connect=`, and `peer=` create a
  resource named after the link, so existing target files do not change.
- **`LinkParams.transport` becomes `via`.** `Transport`'s variants map onto
  the resource kinds: `Listen { addr, max_connections }` to `TcpListen`,
  `Connect { addr }` to `TcpConnect`, and `Peer` to a `Peer` backing.
  `metor build` rewrites a peer resource, not the link's params.

A deployment lists the resolvers that turn a peer's name into an address:

| Resolver | When | How |
|---|---|---|
| `static` (default) | build | `metor build` writes each address from `hosts` and fixed ports. |
| `harness` | spawn | `metor run` binds each listener on `127.0.0.1:0` before starting any child. It passes the listeners down with `LISTEN_FDS`/`LISTEN_FDNAMES` and writes the addresses into the dialers' config. `metor run --resolve harness` selects it for one run. |

- **A cyclic system's `connect()` issues `Resolve` and then `Connect`.**
  Every reconnect resolves again. A `Dial` resource holds only its
  address. On io_uring, `Connect` is a socket op linked to a connect op
  (`IORING_OP_SOCKET`, Linux 5.19+). On poll, it is a nonblocking
  `socket()` and `connect`, then a wait for readiness.
- **Readiness.** Under `harness`, a child signals readiness separately, with
  `READY=1` on a notify socket.

## stellarator

stellarator keeps its own executor and ops. It gains two small pieces:
- **`Executor::turn`** runs one pass without blocking, with the executor
  installed as the thread's current one, and restores the previous one
  after. It never moves a clock it does not own. `Clock::Sim` reads a
  thread-local time that the caller sets.
- **`TcpListener::adopt`** takes a `std::net::TcpListener` that is
  already bound and listening.

| Backend | Sockets, CAN | Files, tty | Quick ioctls (termios, GPIO) |
|---|---|---|---|
| `UringOs` | native | native | inline in `submit` |
| `PollOs` (Unix) | try, then wait for readiness | inline | inline |
| sim | models | models | models |

Only Linux flies, and Linux 5.19 is the minimum. io_uring has no generic ioctl op, so quick ioctls run
inline, and the system still sees the result next cycle.

## Guests

- **The same surface.** A wasm or dylib system takes `Cap<K>` and allocates
  through `IoInit`, like any other system. It cannot take a `DeviceSide`
  in v1: a model needs the target's `Tables`.
- **The buffer table crosses as one region,** like a ring. The region is
  the arena, with its directory inside it.
  - `metor_fsw_create` receives it alongside the rings.
  - The pack runs the ctor, so it freezes the arena after the first make
    and rewinds it before each later one. The host only reads it. Neither
    side keeps a copy of the directory.
  - A dylib shares the region. A `DlSlot` is a member too, and every
    candidate it loads gets the same region.
  - For a wasm guest, the adapter copies the buffers of submitted ops out and
    of completed ops in, around each step.
- **The ABI.** The definition JSON carries each system's `GrantDef`s.
  Together with the new region, this makes ABI 10, so packs are rebuilt.
